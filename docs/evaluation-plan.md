# guoAppGo 技术评估（二）：路线、工期与风险

> 版本基准、原应用规模与两套技术栈现状见 [evaluation.md](evaluation.md)；本文第 5–8 节沿用那里的数据与结论，章节编号接续（从 5 开始）。

---

## 5. 三条路线取舍

### 5.0 先纠正一个前提

**moejs 不提供 UI，也不提供 webview**。所以"全 Go 原生 UI / Go+webview / Go+moejs 混合"不是三个并列的 UI 方案：moejs 与 UI 选择正交。真正要决策的是 **A（原生 UI）还是 B（webview）**，以及"站源引擎用 goja 还是 moejs"。下文 C 指"原生壳 + webview 播放页"这一折中形态。

### 5.1 方案对比

| | A 全 Go 原生 UI | B Go + webview 前端（**推荐**） | C 原生壳 + webview 播放页 |
| --- | --- | --- | --- |
| 做法 | MyGo `ui` 包手写 19 个页面 + 播放器 | Go 做核心/IPC/窗口，前端 TS/Vue 写 19 页；播放器用 `<video>` + hls.js + 现有代理 | 列表/设置等用原生 `ui`，播放页用 `ui.WebView` 嵌网页 |
| 交付物 | 单二进制，无 webview 进程 | 单二进制 + 内嵌前端资源 | 混合，两套 UI 技术 |
| 现实工作量 | 142 人天（单源 133） | **117 人天**（单源主口径 **106**；R1 失败 126~136） | 125 人天（单源 115） |
| 主要风险 | 0.9.x 控件库在播放器交互上不够用；无原生 PiP；弹幕/手势要自绘；团队学习曲线 | webview 内存（约 100–200 MB）；Windows 无原生 HLS（须 hls.js）；HEVC 依赖系统 | 两套技术栈都要维护，边界易腐化 |
| 可维护性 | 一套语言，但 UI 层跟着 MyGo 的 breaking 走 | 前后端边界清晰；前端技能栈熟悉，替换成本低 | 最差：两套渲染、两套调试 |
| 性能 | 最优（GPU 直绘、内存低） | 可接受（视频走 GPU，UI 走 webview） | 中 |
| 何时该否决 | 团队不接受 0.9.x UI 库的变动频率；或必须单进程低内存 | 必须保证 Windows HEVC/AV1 全量可播且不能装扩展；或要求 <80 MB 内存 | 团队只有 1 人，维护不了两套 |

### 5.2 推荐 B 的五条理由

1. **团队栈匹配**：团队现有项目是 Vue/TS（plus-ui 等），页面产能最高；A 路线要求全队先学一个每周在变的 Go UI 库。
2. **播放器周边是 web 的成熟区**：画中画、全屏、字幕、弹幕（DOM/Canvas）、手势，浏览器里都是现成解法；而 MyGo 原生 UI 的画中画**只支持页面内 `<video>`**，选 A 等于自断一臂。
3. **取流问题已被现有代码解决**：`app_stream.go` 已经是"本地 HTTP 代理 + 自定义头 + CENC 解密"，webview 与原生播放器都能吃这个代理，B 不需要新造轮子。
4. **HLS 在两个平台都有解**：macOS WKWebView 原生支持 HLS；Windows WebView2 是 Chromium，**不原生支持 HLS**，用 hls.js + MSE 覆盖（需代理提供 CORS）。这一点必须在 spike 里验证，见 R1。
5. **可撤退**：UI 与 Go 核心通过 IPC 解耦，将来若 MyGo 原生 UI 成熟（或团队想换壳），只换外壳，核心不动。

**但 B 是条件推荐，不是无条件推荐。** B 的 117 人天（单源 106）成立的前提是 **R1 通过**——"播放也塞进 webview"这条路走得通。若 R1 失败、改走"嵌 mpv"的退路，B 的现实值变成 **137~147**（单源 **126~136**），与 A 的 142（单源 133）是同一量级，此时选型要重比，而不是硬着头皮上 B。**决策看失败路径，不看 106/117。**

**否决条件（写清楚，避免"到时再说"）**：

- 若真实站源里 HEVC/AV1 占比高、且 Windows 用户不能要求装系统扩展 → 加 native module 嵌 mpv/ffmpeg，B 的成本 +20~30 人天；此时 A 也要加同样的成本，B 仍不吃亏。
- 若产品要求"单进程、内存 <80 MB、冷启动 <300 ms" → 选 A。
- 若团队只剩 1 名工程师且不熟前端 → 选 A（一个人维护两套技术栈会烂尾）。

## 6. 工作量估算

### 6.1 口径（必须先读）

- 1 人天 = **6 小时有效产出**；含单元测试与文档；**表中为人天小计，合计再加 10% 缓冲**；不含 spike（另计 5 人天，见第 7 节）。
- 基准人：**1 名熟悉 Go、不熟悉 MyGo、有前端经验的工程师**；2 人并行按 **0.85** 效率折算（沟通与合并损耗）。
- 不含：UI 设计稿重做（沿用现有信息架构与视觉）、iOS/Android、Linux、上架商店、站源抓取规则重写。
- 与理清对齐后单列的两项：**M13 进程模型/生命周期**（`release`/`cancelPlayback`/`workLease` 是给 Flutter 优雅关停用的，Go 变主程序后要重做，不能算进功能模块）；**M5 含 ffmpeg 集成**（Go 侧现有 `ffmpeg` 调用为 0）。

### 6.4 路线 C 与日历换算

- C（原生壳 + webview 播放页）：**74 / 125 / 215 人天**（两套 UI 技术，M1/M3 各取一部分，再加边界维护）。
- 换算（多源口径）：B 的 117 人天 ÷ 2 人 ÷ 0.85 ≈ **69 个工作日 ≈ 14 周**（R1 通过时）；A 的 142 人天 ≈ **84 个工作日 ≈ 17 周**；C ≈ 15 周。**单源主口径**：B 106 ≈ 62 个工作日 ≈ **12.5 周**，A 133 ≈ 78 个工作日 ≈ 15.5 周。B 失败路径（多源 137~147 / 单源 126~136）约 **16 周**，与 A 持平。
- **单源已定**（Chief 2026-11-17 拍板，v1 只做红果）：B 现实 **106 人天**（2 人约 12.5 周），A **133 人天**（约 16 周）。这省下的不只是 11 人天，而是整个模块层（880 行 JS 桥 + 商店索引 + 白名单校验）及其未验证的 alpha 引擎依赖；代价是站源单点，多源放 v2。6.2/6.3 表里的 142/117 保留作**多源口径**，决策主口径是 106。
- 若只有 1 人：B ≈ 117 个工作日（约 6 个月），A ≈ 7 个月，且 A 的个人学习曲线风险更高。

## 7. 风险与验证（含 A/B 选型的先决条件）

每个风险都给出"半天到 2 天能做完"的验证动作；验证不通过就按"退路"调整方案，不等开工后才发现。

### R0 B 路线成不成立：播放能不能塞进 webview（决定选 A 还是 B）

- **为什么单列**：B 的全部优势押在这一条上。它不成立时 B 的现实值从 117 变成 **137~147**，与 A 的 142 持平，选型结论会翻转——所以它不是"五个风险之一"，是**选型门槛**。
- **验证动作**：即 R1 的第一阶段：macOS WKWebView 与 Windows 11 WebView2 各播 3 个真实源（HLS/TS+AES-128、fMP4/HLS、红果 v5 签名）30 分钟，共 2 人天。**关键点是 CENC 解密后喂片源**——原应用这段在 Go 里（`app_stream_cenc.go`），webview 只能吃代理吐出的明文流，必须验证"代理 → MSE"这条链不额外引入延迟或断流。
- **必须带对照组**（理清提出，`feature-inventory.md` §11 第 2 条）：同一批源、同一网络、同一时段，用原 Flutter 应用（tag `app-v2.0.1-113`，media_kit 1.2.6 + ffmpeg_kit）跑同样 30 分钟，记录同一组指标。理由：tag 相比 2.0.2 缺取流/重连修复（`playback_session.dart` +54/−14 等 18 处集中在播放线），红果还有 v5 签名（#165）变量；没有对照组，首帧/seek 不达标时无法区分"webview+MSE 撑不住"和"继承 tag 的取流缺陷"。
- **判定**：两端都能播，**且不劣于对照组**（首帧 ≤2 s、seek 后恢复 ≤1.5 s、内存峰值 ≤400 MB 作为绝对线）→ B 成立，按 **106** 立项。若新栈达标但对照组同等抖动，判为源/网络问题，不据此否决 B。
- **不成立**：不直接判 B 死。把 B 的报价改成 126~136 再与 A 比；若仍选 B，M3 追加 native module 嵌 mpv。
- **并行安全区**：M0/M1/M2/M7/M12（约 45 人天）不受这条影响，spike 期间可先推，不必等结果。

### R1 解码与取流能不能覆盖真实站源（最高风险）

- **为什么现在验**：这条决定 B 能否成立，也决定要不要嵌 mpv。
- **验证动作（2 人天）**：用现有 `native/core` 的本地代理（`app_stream.go`）接 3 个真实源：① HLS（TS 分片 + AES-128）② fMP4/HLS ③ 红果 v5 签名源；分别在 macOS arm64（WKWebView + `<video>`）与 Windows 11（WebView2 + hls.js）播 30 分钟，记录首帧时间、拖动 5 次后的恢复时间、内存峰值、失败率。**必须同源同网同时段跑原 Flutter 应用（tag `app-v2.0.1-113`）作对照组**，理由见 R0。
- **判定阈值**：首帧 ≤ 2 s、seek 后恢复 ≤ 1.5 s、30 分钟无中断、内存峰值 ≤ 400 MB，**且不劣于对照组**。
- **不通过退路**：Windows 限定 H.264 源；或加 native module 嵌 mpv/ffmpeg（+20~30 人天，需重估）。

### R2 播放器交互与弹幕在目标栈上的还原度

- **为什么现在验**：这是原应用最"重"的 8,891 行，也是重写后用户第一眼能感知的差异。
- **验证动作（1.5 人天）**：按 8 项清单做可点击 spike——单击暂停、双击全屏、左右滑动 seek、上下滑动音量/亮度、长按倍速、锁屏、选集切集、弹幕开关与密度。B 在 webview 里做，A 在 `ui` 包里做，各出一张"可做/难做/做不了"的表。
- **判定阈值**：8 项里 ≥ 7 项在 1.5 人天内做到"接近原体验"。
- **不通过退路**：换 C（播放页单独用成熟技术），或把难项降级（如去掉滑动调亮度）。

### R3 MyGo 0.9.x 的变更频率与维护风险

- **为什么现在验**：7 周 83 个 release、5 天 146 commits，且 12 个版本提过 breaking；锁版只是止血，升级是长期成本。
- **验证动作（0.5 人天）**：搭一个最小工程，锁 `v0.9.2` 跑 `go test ./...`；再用 `apidiff`（或 `go doc` 快照 diff）对比 `v0.9.1`→`v0.9.2` 的导出声表面；同时记录一次"升级一个小版本"实际要改多少行。
- **判定阈值**：单次 minor 升级改动 ≤ 50 行，且不需要改业务逻辑。
- **不通过退路**：把 MyGo 调用面收敛到一个内部 `platform` 包（UI 和窗口 API 全部经它），升级只改一处；必要时冻结版本到发版。

### R4 moejs 0.1.1 的成熟度

- **为什么现在验**：0.x、两周两个正式版、依赖 alpha、查不到生产案例；但它决定"站源模块"这一层要不要现在换引擎。
- **验证动作（1 人天）**：定义 `script.Engine` 接口；用 3 个真实站源模块（1 个内置 + 2 个在线）分别在 goja 与 moejs 下跑同一批请求（目录页、搜索、详情、取流），对比输出 JSON。
- **判定阈值**：diff 为 0；且 moejs 侧无 panic、无超时；CommonJS wrapper 不超过 200 行。
- **不通过退路**：保留 goja 作默认，moejs 只作实验实现，不进发布分支。
- **前置门槛**：v1 已定单源（只做红果），模块系统整层不做，本风险在 v1 消失：moejs 不进 `go.mod`、不写 ADR。v2 恢复多源时再按本节验证。

### R5 分发合规与签名（容易被低估）

- **为什么现在验**：macOS 公证需要开发者账号与 App-specific password；Windows 安装包签名需要证书；原项目 GPLv3 + GPL 版 ffmpeg 会传染发布方式。
- **验证动作（1 人天）**：用 `mygo build` 走一次完整的 macOS 签名 + 公证 + staple（哪怕空壳应用）；Windows 用自签证书跑一次 MSI 安装 + 自动更新签名校验；同时确认 guoAppGo 的许可证选择（GPLv3 兼容 / 闭源则不用原代码与 ffmpeg）。
- **判定阈值**：公证通过且 Gatekeeper 离线可开；Windows 安装、升级、卸载干净。
- **不通过退路**：先出未签名开发版内测；GPL 问题由产品侧拍板（闭源则移除 ffmpeg，改用纯 Go 合并，M5 +8 人天）。

## 附录 B：给下一轮的三条输入

1. **理清**的 P0 清单直接决定 M2/M3 的范围；若按可砍的 8–9k 行 Dart 折算，现实工期可压到 B 的 **约 90 人天**（原 117），但播放器与转码两块不会缩。
2. **戈**的 spike 若证明 WebView2 + hls.js 在 Windows 上 HLS 可用（含 CENC 解密后经代理喂 MSE），R1 的退路（嵌 mpv）就可以暂缓，B 路线按 106 人天立项（多源 117）；若不通过，B 报到 **126~136**（多源 137~147）再与 A 比，不要在对话里先拍 B。
3. **文档**的 ADR 清单里，ADR-0002（UI 路线）在本报告已有推荐与否决条件；ADR-0003（播放内核）要等 R1 的实测数据；**ADR-0009 不写**——v1 单源已定，模块层不做；v2 若恢复多源，再并成"v2 站源策略"一条落。
